## Windows findings and fixes

1. Reproduced signature verification failure in Node: inherited PowerShell 7
   module paths made Windows PowerShell unable to load Microsoft.PowerShell.Security.
   The verifier now invokes the system Windows PowerShell by absolute path, uses
   only its system module directory, fails on script errors, and has a bounded
   execution timeout. It does not modify the machine's trust store.
2. The signed V2 release envelope was checked in the renderer but was not checked
   again by the main-process install service. Windows installation now requires
   a valid Ed25519 envelope at that boundary before any download or file creation.
   Signed metadata is bound to the exact GitHub tag/path, artifact, size, hash,
   product identity, expected version, minimum updater version and pinned signer.
   Renderer-supplied unsigned metadata alone cannot initiate installation.
3. Main-process version comparison now distinguishes preview versions from stable
   versions, avoiding false post-install success for an older preview.
4. Real Windows signature tests no longer skip module-loading failures. Tests
   check the signed 3.1.0 fixture, reject wrong product versions, and reject an
   altered copy of the signed executable. Original artifacts are unchanged.
5. Release-gate tests now exercise every missing gate rather than requiring
   qualification evidence to remain permanently false.

The V1 compatibility manifest remains part of release assembly for installed
3.1.0 clients. These source fixes cannot retroactively change those clients.

  It is present in this PC's CurrentUser Root store. Local Authenticode `Valid`
  therefore does not demonstrate validation on a clean customer's PC.
  The user confirmed no other production signing certificate is available.
- The pinned-certificate updater policy has now been narrowed to the documented
  Windows trust result: `Valid` is accepted, and `NotTrusted` is accepted only for
  Orion's exact pinned, self-signed certificate after the signed Ed25519 envelope,
  exact artifact hash, version, URL and signer identity have already been verified.
  `UnknownError`, `HashMismatch`, `NotSigned`, a different signer, a non-self-signed
  certificate and invalid certificate dates/EKU remain rejected. This clean-machine
  branch still requires physical validation on a PC that does not trust the Orion
  certificate before Preview publication.
- The four GitHub approval environments were created successfully. A persistent
  self-hosted runner was intentionally not registered on the normal development PC
  because the repository is public. Release preparation and signing are therefore
  local-only on the protected Windows account; GitHub Actions is reserved for the
  approved Preview and Stable publication gates and re-verifies the uploaded bundle.
- No final signed Desktop 3.2.0 candidate exists yet. Exact-byte clean install,
  production 3.1.0 Preview-channel in-app upgrade, failure recovery, and post-restart
  confirmation remain unrecorded. No draft/preview/stable release was created.
- Signed simulated future-release tests exercise verification and compatibility
  using ephemeral test keys; they are not physical future-install or bridge-flow
  acceptance. Complete the full qualification checklist before promotion.

Windows reputation warnings are separate from Orion's integrity checks. A
self-signed certificate does not acquire public Windows trust merely because
Orion pins it. Even publicly trusted signing does not guarantee immediate
SmartScreen reputation. See [Microsoft's SmartScreen signing guidance](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation).
