Orion Mobile audit verdict
Orion Mobile is currently a promising internal alpha / functional prototype, not a release-ready mobile application.
The catalog and navigation experience is reasonably developed, and Smart Remote has real desktop integration. However, playback reliability, offline downloads, authentication/sync, accessibility, source health, testing, and repository reproducibility remain incomplete.
The most urgent issue is structural: almost the entire mobile/shared monorepo migration is currently untracked. A clean clone would not reproduce this mobile app.

Partial or misleading features
Streaming player
The existing player is almost entirely an embedded WebView player. A native expo-video implementation exists, but it is never selected by the route.
The route always returns EmbedVideoPlayer in [player/[id\].tsx (line 388)](C:/Projects/Orion - A Multiverse of Stories/apps/mobile/app/player/[id].tsx:388). These items are therefore dormant:
NativeVideoPlayer.
StreamExtractor.
extractedUrl.
useEmbedFallback.
Native seeking and progress tracking.
Reliable direct HLS/MP4 playback.
Native offline playback.
The existing player scrubber is also static. It shows fixed 00:00, --:--, and 30% progress rather than actual playback data.
Watchdog and failover
The embedded player does not obtain true playback/buffering state. It simply clears buffering after four seconds in [player/[id\].tsx (line 133)](C:/Projects/Orion - A Multiverse of Stories/apps/mobile/app/player/[id].tsx:133).
Consequences:
A broken player iframe may be classified as loaded.
A video that loads its page but not its media will not trigger reliable recovery.
The 15-second watchdog is driven by page-loading state, not video state.
Failover uses getNextNonAsyncSource, not the existing health-aware selector.
Experimental sources can be selected without runtime validation.
The shared package already has getNextHealthyNonAsyncSource, but mobile does not use it.
Source ID routing
The player passes only { tmdbId: id } into every source in [player/[id\].tsx (line 380)](C:/Projects/Orion - A Multiverse of Stories/apps/mobile/app/player/[id].tsx:380).
Sources marked imdb-preferred therefore receive TMDB IDs when no IMDb lookup has occurred. Depending on provider behavior, that can produce empty or incorrect streams.
The Sources sheet also hard-codes claims such as “HIGH SPEED” and “STABLE” in [SourcesSheet.tsx (line 17)](C:/Projects/Orion - A Multiverse of Stories/apps/mobile/src/components/player/SourcesSheet.tsx:17) without measuring source startup, success, subtitle health or failure rate.
Ad blocking
Current blocking is a short hostname/DOM-selector list injected into each WebView.
It does not provide:
Provider-specific allow/block rules.
Redirect-chain classification.
Navigation-domain validation.
New-window handling.
Request diagnostics.
Protection against first-party ad scripts.
Provider subtitle-domain exceptions.
Regularly maintained filter data.
This will inevitably work for some sources and fail on others.
Smart Remote
The remote command bridge is genuine and most mobile commands have corresponding desktop handlers. Its security and lifecycle remain incomplete.
Confirmed problems:
Desktop initially uses a fixed PIN, 3566, in [smartConnectIpc.js (line 12)](C:/Projects/Orion - A Multiverse of Stories/apps/desktop/src/main/ipc/smartConnectIpc.js:12).
No PIN expiry, attempt throttling or temporary lockout.
Server binds to every interface at 0.0.0.0.
Cleartext HTTP is enabled.
Wildcard CORS is allowed in [smartConnectIpc.js (line 70)](C:/Projects/Orion - A Multiverse of Stories/apps/desktop/src/main/ipc/smartConnectIpc.js:70).
Unauthenticated /api/status exposes paired-device and current-playback information.
Tokens are memory-only and are lost after desktop restart.
Mobile polls every 1.5 seconds, even when the Connect screen is inactive.
Status sets isConnected from the desktop’s global paired flag, not from proof that this phone’s token is valid.
IP and pair-state persistence still use localStorage in [connect.tsx (line 162)](C:/Projects/Orion - A Multiverse of Stories/apps/mobile/app/(tabs\)/connect.tsx:162), which is unsuitable for reliable React Native persistence.
There is no mDNS/Zeroconf discovery; pairing is manual IP/QR probing.
Default phone target 127.0.0.1 points back to the phone, not the desktop.
Smart Remote is usable for controlled local testing, but not ready to be advertised as hardened pairing.
Dead or disconnected features
Mobile downloader
The Downloads page explicitly says “Downloader Locked” in [downloads.tsx (line 39)](C:/Projects/Orion - A Multiverse of Stories/apps/mobile/app/(tabs\)/downloads.tsx:39), and the modal says “Downloader Coming Soon” in [DownloadModal.tsx (line 42)](C:/Projects/Orion - A Multiverse of Stories/apps/mobile/src/components/DownloadModal.tsx:42).
A separate downloader service exists, but it must not be enabled in its current form:
Fabricates progress using a timer.
Uses browser localStorage.
Downloads entire responses into Blob memory.
Does not support background downloading.
Does not support native file storage.
Does not handle HLS manifests/fragments correctly.
Blob URLs disappear after restart.
On error, it records the job as completed in [downloadManager.ts (line 141)](C:/Projects/Orion - A Multiverse of Stories/apps/mobile/src/services/downloadManager.ts:141).
“Offline” media may only retain the original remote URL.
This is dead experimental code and should either be removed from production paths or replaced with a native background download architecture.
Offline playback
offlineUri is passed into the same embed player rather than the native video component. Even a valid local file would therefore be treated as a WebView page.
Offline playback is not functional.
Subtitle service
A SubDL/Wyzie helper exists, but no UI or player imports it. Therefore:
Subtitle search is disconnected.
Language selection is absent.
Provider subtitles are not captured.
External subtitles are not injected into the player.
Sidecar subtitle playback is absent.
More seriously, fallback provider credentials are hard-coded into renderer/mobile source at [subtitles.ts (line 13)](C:/Projects/Orion - A Multiverse of Stories/apps/mobile/src/services/subtitles.ts:13). Expo public variables are bundled and extractable, so this is not credential protection.
The declared Wyzie key is not used by the actual request.
History and Continue Watching
The context loads history and progress, but there are no public setters and no player writes either value.
The Library says watched items will “automatically appear,” but only explicit manual markWatched actions create entries.
Additional defect: clearHistory clears the watched map, not the separately loaded history record, in [LibraryContext.tsx (line 153)](C:/Projects/Orion - A Multiverse of Stories/apps/mobile/src/context/LibraryContext.tsx:153).

Library and data concerns
My List persistence works on native when MMKV initializes.
If MMKV fails, storage silently becomes memory-only and all data disappears after restart.
Web also uses memory-only storage, despite being exportable.
No schema version or migration strategy.
No data validation for corrupt stored records.
No metadata repair/refetch.
Saved sorting and manual reordering are absent.
History and progress storage are structurally present but inactive.
No backup integration.
No account-scoped data separation.
No cache size controls.
No logout/data deletion lifecycle.

Android and iOS
The generated Android folder is intentionally ignored, which is normal for Expo prebuild, but the local generated project still shows:
Release builds signed with the debug keystore.
versionCode 1.
versionName 2.0.0.
Cleartext traffic enabled.
Broad permissions including recording audio, overlay, external storage and settings modification.
Portrait application/activity configuration despite player landscape locking.
Because Android is ignored, these settings must be represented correctly through Expo config/plugins or they disappear on a clean prebuild.
iOS has no bundle identifier or release configuration beyond tablet support. No iOS build has been proven.
Security and privacy concerns
Highest priority concerns:
Hard-coded subtitle provider credentials.
Publicly bundled TMDB token—acceptable only if treated as a public application identifier with suitable restrictions, never as a secret.
Cleartext Smart Connect traffic on the LAN.
Fixed four-digit initial PIN.
No brute-force rate limiting or PIN expiry.
Unauthenticated playback/device metadata from /api/status.
Wildcard CORS on the desktop LAN server.
Pair tokens lost on desktop restart.
No privacy screen, account/data deletion or backup consent.
Third-party embeds can execute arbitrary provider JavaScript inside WebView.
Ad blocking does not create a security boundary.
Mobile store policy risk from unverified third-party streaming embeds and downloading claims.
